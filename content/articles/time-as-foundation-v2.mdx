# Time as a Foundation

Every piece of content on rendered_useful has a date. But time is so much more than chronological order. Time creates relationships between content. Time bounds events. Time tells stories.

If I want this platform to support real creative work, not just display it, time needs to be a first-class concept from the beginning.

**And now it is.** Series, Events, and Versions are live. This article explains the philosophy behind them and shows you how they work.

## The Problem with Dates as Metadata

Most content platforms treat time as metadata. A published date. Maybe an updated date. It gets stored, displayed, and used for sorting. That's it.

This works fine for standalone content. But creative work rarely exists in isolation.

- A tutorial series unfolds over weeks
- A game jam has a start and end date
- A build log documents progress over months
- A challenge like Inktober spans exactly 31 days

When time is just metadata, you can't express any of this. You end up with workarounds: naming conventions ("Part 1", "Part 2"), manual linking, or external organization.

I want time to be structural, not decorative.

## How Series Work

A series is an ordered collection of content. Each piece knows its position through simple frontmatter:

```yaml
---
title: "Time as a Foundation"
series: "platform-foundations"
seriesOrder: 2
---
```

That's it. The platform handles the rest:
- **Navigation** appears automatically (← Previous / Next →)
- **Series info** shows your position ("2 of 2" or "2 of 2+" for ongoing series)
- **Series pages** collect all parts with descriptions

Series have a status: `ongoing`, `completed`, or `paused`. This tells readers whether to expect more.

## How Events Work

An event is a time-bounded container. It has dates, not just an order.

```typescript
{
  slug: 'preliminary-foundations-hackathon',
  title: 'Preliminary Foundations Hackathon',
  startDate: '2026-01-13',
  endDate: '2026-01-20',
  communities: ['rendered-useful', 'opensource'],
  metadata: {
    theme: { value: 'Foundations', display: 'hero' },
    goals: { value: '...', display: 'markdown' },
  }
}
```

Content tags itself as part of an event:

```yaml
---
title: "Time as a Foundation"
event: "preliminary-foundations-hackathon"
---
```

The event page automatically:
- Shows **status** (Upcoming / Live Now / Ended)
- Displays **date range** with countdown or time remaining
- Collects **all submissions** tagged with that event
- Renders **custom metadata** (themes, rules, goals) with flexible display options

## How Versions Work

Versions let content evolve while preserving history. Add version fields to any article, project, or event:

```yaml
---
title: "Time as a Foundation"
version: "2.0"
versionGroup: "time-as-foundation"
versionNote: "Added Versions section"
---
```

The `versionGroup` connects different versions of the same content. The platform:
- Shows a **version selector** dropdown when multiple versions exist
- Defaults to the **latest version** (newest date)
- Displays an **"older version" banner** with a link to latest when viewing old versions
- Tracks **version notes** so readers know what changed

## How Time Works Today

Before building series and events, I needed to get the basics right. Dates are now handled properly:

**Storage**: All dates are stored in UTC (ISO 8601 format). This ensures consistency regardless of where content was created or where the server is located.

**Display**: Dates are rendered in the user's local timezone using the browser's `Intl` API. If you're in Tokyo, you see Tokyo time. If you're in New York, you see New York time.

```typescript
// Parse a UTC date string
export function parseUTCDate(dateString: string): Date {
  if (/^\d{4}-\d{2}-\d{2}$/.test(dateString)) {
    return new Date(dateString + 'T00:00:00Z')
  }
  return new Date(dateString)
}

// Format for display in user's timezone
export function formatDate(dateString: string, options = {}): string {
  const date = parseUTCDate(dateString)
  return date.toLocaleDateString(undefined, formatOptions)
}
```

The `undefined` locale lets the browser use the user's preferred language and date format automatically.

This also includes utilities for:
- Relative time ("2 days ago", "in 3 hours")
- Date comparison for sorting
- Range checking for events
- Timezone detection

Small foundation, but it matters. Every feature that involves time will build on this.

## Connecting Time to Communities

Time and communities intersect naturally:

- A **Game Development** community might host recurring game jams
- A **Learners** community might run study groups with start/end dates
- A **Writers** community might coordinate NaNoWriMo participation

Events belong to communities. Series can too. Activity feeds show what's happening in your communities over time.

This is where things get interesting. Time isn't just about individual content. It's about collective activity.

## Why This Matters

I keep coming back to the same idea: rendered_useful should support real creative work, not just showcase it.

Real creative work happens over time. Projects evolve. Things unfold. Events bring people together around deadlines. Challenges create shared moments.

If time is just a sort field, none of that is possible in the platform itself. It has to happen elsewhere.

But if time is structural, if series and events and versions are first-class concepts, then the platform can actually support how creative work happens.

That was the goal. And now it's real.

---

## Future Exploration

One question I'm still thinking about: can you have a *series of events* or an *event of series*? Right now, Series and Events are independent concepts. Content can belong to both, but they don't nest inside each other.

There's something interesting there. A recurring game jam could be a series of events. A tutorial series created during a hackathon could be an event containing a series. I'm not sure what makes sense yet, and there are other foundational things I need to address before expanding the time foundation further. But it's on my mind.
